# macOS: сигналы, окна и поставка

## Измеренный нативный адаптер

Swift CLI `native/MediaProbe.swift` с Foundation/CoreAudio/CoreMediaIO/AVFoundation компилируется `npm run build -- --native`; JSON через stdout, таймаут вызова 2 секунды, максимум 128 КБ. Он поставляется как доверенный ресурс Electron. Отдельный простой процесс выбран вместо ABI-модуля: нет привязки к Node ABI, сбой адаптера не завершает приложение. Чтение выполняется по запросу, а не бесконечным высокочастотным polling.

|Сигнал|Поддерживаемый API|Семантика и ограничения|Результат 02.10.2026 на MacBook Air M4 / 27.0|
|---|---|---|---|
|Аудиоустройство с входом|CoreAudio `kAudioDevicePropertyDeviceIsRunningSomewhere`, фильтр input streams|Активность устройства, не доказательство звонка, передачи голоса или mute. У duplex-устройства может отражать вывод.|Адаптер выполнен; inactive для перечисленных устройств в момент теста. Включение другим приложением не проверено.|
|Камера|CoreMediaIO `kCMIODevicePropertyDeviceIsRunningSomewhere`|Только перечисленные CMIO устройства; приложение-источник неизвестно; виртуальные/неперечисленные устройства могут не покрываться.|Адаптер выполнен; inactive для перечисленных устройств в момент теста. Браузер/видеозвонок не проверены.|
|Чужой захват экрана|Нет публичного общего API наблюдения|ScreenCaptureKit разрешает захват, но не является монитором всех чужих захватов.|unsupported|
|Mute звонка|Зависит от приложения|Нельзя вывести из активности микрофона.|unsupported|

Источники: https://developer.apple.com/documentation/coreaudio/kaudiodevicepropertydeviceisrunningsomewhere и https://developer.apple.com/documentation/coremediaio/kcmiodevicepropertydeviceisrunningsomewhere . Разрешение на захват не равно фактической активности. Нет доступного устройства/ошибка запроса → unknown. Отсутствие разрешения при известном отказе должно отличаться от inactive; текущие query API не дают надёжного универсального различения отказа и недоступности, поэтому возвращается unknown. Не подтверждён глобальный индикатор «всё выключено».

## Общая полка, быстрый запуск и история буфера

`src/main/shelf.ts` владеет единственным окном `mode=shelf`: отдельного окна launcher больше нет. Наведение, меню и сочетание быстрого запуска повторно открывают историю буфера, сниппеты или эмодзи, если полка была закрыта меньше минуты назад; после минуты открывается список программ. Renderer восстанавливает запрос, выбранную запись, просмотр с преобразованием, незавершённый редактор сниппета, категорию/оттенок эмодзи и прокрутку. Явное открытие встроенного приложения начинает свежий поиск. Сочетание истории и её пункты меню явно открывают `builtin:clipboard` в том же окне. Реестр встроенных приложений находится в `src/shared/launcher.ts`; история и связанные настройки буфера хранятся отдельно от SQLite-настроек приложения.

`ShelfLifecycle` различает `hidden`, `preparing`, `open` и `closing`. Revision защищает подтверждения показа и завершения скрытия от устаревших ответов; sessionId меняется только при новом открытии и сохраняется при навигации. Закрытие запоминает только показанное назначение; повторное скрытие и отменённая подготовка не продлевают минутный срок. Renderer атомарно применяет назначение и контекст перед `didShow`, сохраняет только последний подтверждённый встроенный экран и сбрасывает меню, ошибки, подтверждения и занятость при входе.

Цель вставки принадлежит одному открытию: навигация сохраняет её, обычное закрытие отменяет, новое открытие захватывает новую. Автовставка забирает одноразовую цель перед скрытием; новый сеанс отменяет старую вставку. Кнопка разрешения скрывает полку и оставляет её закрытой. Системный диалог сохранения подавляет закрытие по blur/наведению; фокус возвращается только в текущем сеансе.

`Shelf.tsx` отвечает за геометрию и анимацию оболочки; `Launcher.tsx` — за поиск и переходы, `ClipboardHistory.tsx` — за историю. Явная команда возврата к приложениям всегда открывает список. Пока полка видна, минутный таймер не сбрасывает представление; сон и блокировка сохраняют свои ограничения. Настройка наведения находится в «Полка и сочетания»; сохранённое значение используется без миграции.

Верхние углы прямые: `roundedCorners: false` отключает нативное скругление, нижние углы задаются CSS. Панель присоединяется к Spaces с `skipTransformProcessType: true`: её первое создание не должно менять activation policy всего приложения и скрывать значок Dock. Полка использует неактивирующую панель `type: panel`: приложение, активное до открытия, сохраняет меню в строке macOS. Вызов `app.focus()` здесь не нужен. И наведение, и открытие клавиатурой вызывают `show()` / `focus()` и передают фокус поиску: стрелки и Enter работают без предварительного щелчка. Намерение фокуса входит в снимок состояния, поэтому не теряется при поздней подписке renderer на события.

Чёрная панель начинается у верхнего края дисплея и визуально объединяется с вырезом; заголовок слева и кнопки справа располагаются на уровне camera safe area, с пустой центральной областью по ширине выреза. Поиск и список находятся ниже выреза. `enableLargerThanScreen` разрешает положение выше обычной границы строки меню, уровень `pop-up-menu` сохраняет видимость панели. Открытие за 200 мс раскрывает маску от размера выреза, закрытие за 150 мс сворачивает её обратно. Нативное окно скрывается после подтверждения анимации, с резервным таймером; повторное открытие отменяет ожидающее скрытие. При reduced motion переход выполняется сразу. `npm run test:desktop -- clipboard-animation` проверяет реальную координату окна, фон, отступы, повторное открытие и reduced motion.

`native/ClipboardProbe.swift` собирается той же командой `npm run build -- --native` и поставляется как ресурс `clipboard-probe`. Процесс проверяет `NSPasteboard.changeCount` раз в 300 мс и сообщает только об изменениях; содержимое читает главный процесс через асинхронный Electron Clipboard API. Начальное содержимое не импортируется. При выходе помощник завершается, а незавершённая запись истории ожидается перед остановкой ядра.

Помощник также сообщает геометрию `NSScreen.safeAreaInsets` и областей `auxiliaryTopLeftArea` / `auxiliaryTopRightArea`, привязанную к идентификатору дисплея. Главный процесс переводит её в координаты Electron. Указатель проверяется раз в 80 мс; задержка наведения — 350 мс, ухода — 150 мс. Область между вырезом и панелью остаётся активной. На дисплеях без выреза используется верхняя центральная область шириной 96 точек. Оба способа открытия передают фокус панели; уход указателя после наведения по-прежнему закрывает её. Сон и блокировка независимо приостанавливают запись и наведение.

Автовставка использует двусторонний JSON-протокол с `clipboard-probe`. Перед захватом фокуса полкой помощник запоминает `NSRunningApplication`, AX-объекты окна и активного поля; в Electron передаётся только одноразовый токен, без содержимого поля. Переходы внутри полки сохраняют цель. После выбора запись попадает в pasteboard, полка скрывается, помощник поднимает исходное окно и проверяет, что активным стало именно сохранённое поле. Поле получает фокус после активации приложения. Если редактор пересоздал AX-объект, помощник ищет совпадающее текстовое поле в исходном окне по идентификатору или геометрии; содержимое поля не читается. Сохранённый диапазон выделения восстанавливается, если редактор это поддерживает. После стабилизации фокуса помощник отправляет полный Command-V через обычный поток событий `CGEvent.post(tap: .cghidEventTap)`, без повторной отправки. Если приложение завершилось, фокус не восстановился, сменился буфер или пользователь переключился в другую программу, вставка не выполняется. Сон и блокировка отменяют ожидающую вставку.

Разрешение Accessibility проверяется без запроса при открытии. Системный запрос появляется только по кнопке пользователя. Без доступа работает копирование; `pasteOnSelect` можно отключить, а Shift-Enter копирует без вставки. Старые файлы истории читаются с `pasteOnSelect: true` без потери прежних настроек. `npm run test:desktop -- clipboard-paste` использует отдельный тестовый Electron-процесс с двумя полями, проверяет сохранение выделения, потерю фокуса и пересоздание rich-text редактора и восстанавливает буфер; при отсутствии разрешения проверяет fallback и явно сообщает, что нативная вставка не проверена.

История общая для платформы и хранится в `clipboard-history/history.enc` профиля через `safeStorage`. Записи и настройки заменяются атомарно через временный файл. Поддерживаются текст и PNG, ограничение размера и количества, срок хранения, закрепление и исключение стандартных confidential/transient/generated markers. Ошибка помощника или хранилища видна в панели и настройках. Пользовательские инструкции — в [README](../README.md#история-буфера-обмена), проверка — `npm run test:desktop -- clipboard`.

Нативный `clipboard-probe` запускается независимо от истории и синхронизации. При ошибке чтения, расшифровки или формата `history.enc` история и синхронизация блокируются до перезапуска; исходный файл не заменяется. Причина ошибки сохраняется в главном процессе, а IPC передаёт отдельные состояния хранилища, помощника, доступности настроек, разрешения Accessibility и синхронизации. Если настройки внутри истории не прочитаны, наведение, сочетание истории и автовставка отключены; основной запуск полки и копирование эмодзи работают. При ошибке записи уже загруженные записи остаются доступны для просмотра и копирования, но новые не собираются. Ошибка `sync.enc` останавливает только синхронизацию. В панели и настройках есть постоянное сообщение, диагностика и путь к файлу; сброса или временной истории нет. Для восстановления нужно вернуть доступ к хранилищу и перезапустить приложение; перед ручной заменой файла сохранить его зашифрованную копию. Проверка с инъекцией ошибки в отдельном профиле без изменения системного буфера и Keychain: `tsx tests/desktop/clipboard-storage-smoke.ts` после сборки приложения и native helpers.

Действия с записью выполняются через разрешённые IPC-методы главного процесса. Для открытия браузера требуется одна полная ссылка HTTP(S) без учётных данных; открытие происходит только по явной команде. Сохранение изображения использует `dialog.showSaveDialog` с окном полки как владельцем и записывает исходные PNG-байты. Пока диалог открыт, потеря фокуса и наведение не скрывают полку; после отмены или завершения фокус возвращается. Ошибки записи отображаются с возможностью повторить сохранение. Смена регистра рассчитывается из исходного текста и не заменяет запись истории.

## Воспроизводимая проверка на целевой 27.0.1

1. Соберите и запустите подписанную платформу, откройте полку и системный индикатор. Зафиксируйте оборудование, OS build, версии из `system.status`.
2. Запустите `build/media-probe` до, во время и после записи в Photo Booth/QuickTime и браузере с выданным доступом к камере/микрофону. Повторите с внешним устройством, virtual camera и только воспроизведением аудио на duplex-устройстве. Сравните с системным индикатором; не приравнивайте mute к неактивности.
3. Отзовите разрешения, отключите устройство, проверьте unknown/unsupported и диагностический текст. Screen capture чужого приложения остаётся unsupported.
4. Откройте окно на втором экране, отключите монитор. Окно должно остаться доступно. Попробуйте занятое сочетание клавиш — ожидается ошибка без перехвата чужой команды.

Эти пункты — сценарии приёмки, не заявления о выполненных ручных тестах.

## Подпись и обновления

[Установка для пользователей: скрипт, скачивание + Терминал, скачивание + настройки macOS](installation.md).

### Установка через Терминал

На Mac с Apple silicon и macOS 27+:

```sh
curl -fsSL https://raw.githubusercontent.com/mishankov/polka/master/scripts/install.sh | /bin/bash
```

`scripts/install.sh` использует только Bash 3.2 и системные утилиты macOS: Node.js, Homebrew и Xcode не нужны. Команда выполняет скрипт из ветки `master`. Установщик разрешает `/releases/latest` в конкретный тег, затем скачивает ZIP и `checksums.txt` именно этого выпуска. До установки проверяет SHA-256, пути внутри ZIP, идентификатор и версию приложения, а также целостность code signature. SHA-256 из того же GitHub Release проверяет целостность загрузки, но не заменяет независимую проверку издателя или Apple notarization.

Установка идёт в `/Applications/Polka.app`; если каталог недоступен для записи, `sudo` запросит пароль macOS. Работающая Полка должна быть закрыта через «Выйти из Полки». Новая копия сначала готовится во временном каталоге рядом с приложением: quarantine снимается только с неё, подпись проверяется повторно, затем заменяется установленная версия. При ошибке замены предыдущая копия восстанавливается. История, настройки и privacy permissions не изменяются установщиком. После установки приложение открывается, а необходимые разрешения macOS пользователь выдаёт отдельно.

Чтобы сначала просмотреть скрипт или выбрать другой существующий каталог, сохраните его в файл:

```sh
curl -fsSL https://raw.githubusercontent.com/mishankov/polka/master/scripts/install.sh -o install-polka.sh
less install-polka.sh
/bin/bash install-polka.sh --install-dir "$HOME/Applications" --no-launch
```

`--no-launch` оставляет приложение установленным без запуска. При повторной установке штатные обновления внутри Полки остаются доступными.

### Подпись приложения

Локальные и PR-сборки используют ad-hoc подпись (`identity: "-"`). Production-выпуски используют один постоянный self-signed сертификат, без Apple Developer account и notarization. `scripts/release/sign-macos.mjs` подписывает Electron bundle, вложенный код и Swift helpers до создания DMG/ZIP. Для `clipboard-probe`, `media-probe` и `sync-discovery` заданы постоянные identifiers `app.everything.desktop.<имя помощника>`; UUID Mach-O больше не участвует в их идентичности. `hardenedRuntime` отключён, entitlement разрешает JIT.

macOS хранит разрешения по designated requirement (DR). У ad-hoc сборок он привязан к хешу конкретной версии; у self-signed выпусков — к постоянному сертификату и identifier, поэтому новая версия может удовлетворять прежнему DR. [Apple: идентичность кода и privacy permissions](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements), [self-signed сертификаты](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html). Сборка проверяет сертификат по закреплённому SHA-1 fingerprint и отказывается от отсутствующего, неправильного или истёкшего сертификата. SHA-1 здесь — идентификатор для `codesign`, не алгоритм подписи: сертификат использует RSA 3072 и SHA-256.

При переходе с ad-hoc версии пользователям может потребоваться один раз удалить старую запись Polka и выдать разрешение заново в System Settings → Privacy & Security → Accessibility («Device Control and Data Access»). На следующем self-signed обновлении необходимо проверить сохранение доступа. Не меняйте appId, signing identifiers или сертификат между выпусками. Внутри приложения нет сброса TCC или автоматической выдачи разрешений.

Self-signed подпись не устанавливает доверие Gatekeeper к разработчику. Первый скачанный DMG по-прежнему может потребовать «Открыть всё равно»; notarization/stapler не применяются. [Apple: идентичность кода и доверие Gatekeeper](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/AboutCS/AboutCS.html).

Keychain `safeStorage` может запрашивать пароль после каждого self-signed обновления даже при неизменном DR: отдельный partition check использует `cdhash` исполняемого файла. «Разрешать всегда» сохраняет доступ для этого build, но не гарантирует доступ следующей версии. [Apple: выбор partition ID](https://github.com/apple-oss-distributions/Security/blob/main/securityd/src/clientid.cpp#L259-L273). Перед первым обращением к зашифрованной истории установленная macOS-сборка показывает объяснение с именем ключа, паролем связки «Вход», действиями в системном окне и последствиями отказа. Подтверждение хранится в `keychain-notice-version` отдельно от зашифрованных файлов и повторяется для новой версии. Development-сборки не показывают этот диалог. `safeStorage` не предоставляет проверки, которая достоверно предсказывает системный запрос без попытки доступа; объяснение может появиться и когда доступ уже разрешён. При ошибках шифрования/расшифровки инструкция также доступна в сообщении об ошибке, истории и настройках.

`npm run package` создаёт локальную сборку без канала обновлений. `npm run release` создаёт выпуск с нативным Sparkle через pinned `electron-sparkle-updater@0.5.2`. Отдельная Ed25519 подпись архива проверяется публичным ключом, встроенным в `Info.plist`; она не является Apple code signing. Проверка обязательна **до распаковки** (`SUVerifyUpdateBeforeExtraction`). Подпись ZIP и публичный ключ дополнительно проверяются Node.js при выпуске. Открытые GitHub Releases служат единственным хранилищем; отдельный сервер и GitHub Pages не требуются.

## Настройка выпуска (один раз)

На Apple silicon Mac с Node, Xcode Command Line Tools и `gh`:

```sh
npm ci
node scripts/release/build-sparkle.mjs
node_modules/electron-sparkle-updater/native/vendor/bin/generate_keys
node_modules/electron-sparkle-updater/native/vendor/bin/generate_keys -x /secure/path/sparkle-private-key
```

Sparkle создаёт ключ в login Keychain; при наличии ключа использует его. Сохраните защищённую резервную копию. Публичный ключ из вывода `generate_keys` задайте как **variable** `SPARKLE_PUBLIC_KEY` в GitHub environment `release`. Содержимое экспортированного файла задайте как **secret** `SPARKLE_PRIVATE_KEY` в той же среде. Приватный ключ нельзя помещать в Git, артефакты, командные аргументы или логи. Потеря ключа для ad-hoc выпуска может потребовать ручной переустановки пользователями; не генерируйте новый ключ для очередной версии.

Workflow берёт версию приложения и имена архивов из тега GitHub Release (с необязательным префиксом `v`); appcast ссылается на исходный тег. Менять `package.json` для выпуска не требуется.

### Постоянный сертификат подписи (один раз)

Нужен OpenSSL (входит в macOS как LibreSSL; также подходит OpenSSL 3). Создайте сертификат в **новом каталоге вне репозитория**:

```sh
node scripts/release/create-signing-certificate.mjs "$HOME/.config/polka-release-signing"
```

Команда создаёт `identity.p12`, `password.txt`, публичные `certificate.pem` и `fingerprint.txt`. Каталог закрыт для других пользователей, приватные файлы имеют mode 0600; существующий каталог не перезаписывается. Сертификат действует 10 лет. Сохраните защищённую резервную копию всего каталога. Генерировать новый сертификат для каждого выпуска нельзя: это снова потребует выдачи разрешений. Истечение или потеря сертификата требуют плановой смены идентичности и повторного согласия пользователей.

Настройте GitHub environment `release` (значения передаются через stdin, а не аргументы или логи):

```sh
base64 < "$HOME/.config/polka-release-signing/identity.p12" | tr -d '\n' | gh secret set POLKA_SIGNING_P12 --repo mishankov/polka --env release
gh secret set POLKA_SIGNING_PASSWORD --repo mishankov/polka --env release < "$HOME/.config/polka-release-signing/password.txt"
gh variable set POLKA_SIGNING_CERT_SHA1 --repo mishankov/polka --env release < "$HOME/.config/polka-release-signing/fingerprint.txt"
```

Secrets содержат защищённый PKCS#12 и его пароль. Variable закрепляет конкретный сертификат: случайная смена P12 без обновления fingerprint прерывает выпуск. Пользователям не нужно устанавливать сертификат в Keychain или менять настройки доверия.

Для локального выпуска передайте через окружение `RELEASE_REPOSITORY=mishankov/polka`, `SPARKLE_PUBLIC_KEY`, `SPARKLE_PRIVATE_KEY`, `POLKA_SIGNING_P12` (абсолютный путь к `identity.p12` или base64 содержимое), `POLKA_SIGNING_PASSWORD`, `POLKA_SIGNING_CERT_SHA1` и, только для загрузки черновика, `GH_TOKEN`. Необязательный `RELEASE_TAG` задаёт тег и версию; без него используется `v` + версия `package.json`. Apple credentials не нужны.

`release.mjs` импортирует identity в отдельный временный keychain и удаляет его после сборки, в том числе при ошибке. Login keychain, список keychains и настройки доверия не изменяются. Секреты подписи удаляются из окружения дочерних сборочных процессов; в конфигурацию и артефакты они не записываются. Sparkle private key передаётся `sign_update` через stdin. В `release-config.json` остаётся `mac.identity: "-"` для входа в custom hook builder без поиска Apple identity; сам hook обязательно использует закреплённый сертификат и проверяет результат. Production-команда не имеет fallback на ad-hoc.

## Полный поток выпуска

1. Выбрать новый тег версии (`vVERSION` или `VERSION`). Уже опубликованные версии и архивы не заменять.
   Добавить `release-notes/VERSION.json` с описанием изменений на обоих языках. Сборка выпуска требует непустые `ru` и `en` (до 20 000 символов каждый):

   ```json
   {
     "ru": "• Уведомление о новой версии на стартовой полке.\n• Можно обновиться, пропустить версию или отложить напоминание на сутки.",
     "en": "• New version notices on the start shelf.\n• Update now, skip a version, or postpone the reminder for 24 hours."
   }
   ```

   Проверить файл и посмотреть описание GitHub Release можно без npm-зависимостей и ключей подписи:

   ```sh
   node scripts/release/release-notes.mjs vVERSION /tmp/polka-release-notes.md
   ```

   Текст передаётся в `description` соответствующего appcast item как JSON `{ru,en}` и показывается как обычный текст, без HTML. Для старых выпусков без этого поля приложение показывает сообщение об отсутствии примечаний. Workflow и локальная команда `--publish` используют эти же изменения в описании GitHub Release: генератор преобразует `•` в Markdown-списки и добавляет требования, путь обновления и все три способа установки на русском и английском. DMG-ссылки закреплены за тегом выпуска; команда скрипта устанавливает последний стабильный выпуск. [Правила написания примечаний](release-notes.md).
2. Запустить `.github/workflows/release.yml` вручную с тегом `vVERSION` или `npm run release -- --publish` локально.
3. Команда собирает приложение, Swift helpers и Sparkle bridge, упаковывает DMG/ZIP, подписывает готовый ZIP, создаёт `appcast.xml`, проверяет signature/размер/URL/версию, codesign, целостность DMG и packaged shelf smoke.
4. Workflow загружает ZIP, DMG и checksums, затем appcast, обновляет описание GitHub Release из проверенных русских и английских примечаний. При ручном запуске выпуск остаётся черновиком до завершения загрузки, затем workflow публикует его. `npm run release -- --publish` локально только создаёт черновик: его следует опубликовать вручную после проверки. Предпочитайте ручной запуск workflow с черновиком; при событии `release: published` feed временно недоступен, пока сборка и загрузка не завершены. Пререлизы и черновики не попадают в stable latest. Уже публичные assets не перезаписываются; повторная загрузка staging assets разрешена только для черновиков.

Подготовка на Ubuntu сначала разрешает точный commit: существующий тег, `targetCommitish` черновика без тега или текущую default branch для нового выпуска. Примечания читаются через `git show` из этого commit, а не из checkout workflow. Отсутствующие или некорректные переводы останавливают подготовку до создания нового черновика/тега и запуска macOS jobs. Новый тег закрепляется на проверенном SHA; смена тега во время подготовки прерывает выпуск. `--ref` при dispatch выбирает код workflow, но не закрепляет исходники нового выпуска на этой ветке. Повторный запуск существующего старого выпуска, чей commit ещё не содержит генератор примечаний ни в `scripts/release/release-notes.mjs`, ни в прежнем `scripts/release-notes.mjs`, сохраняет прежний поток без примечаний; создавать новые выпуски таким способом нельзя.

Для полного процесса подготовки документации, примечаний, PR, CI и публикации используйте проектный skill [release-project](../.agents/skills/release-project/SKILL.md).

Feed: `https://github.com/mishankov/polka/releases/latest/download/appcast.xml`. Он содержит точный immutable URL ZIP вида `.../releases/download/TAG/polka-VERSION-arm64.zip`, версию, минимальную macOS и Ed25519 signature. GitHub latest должен указывать на новейший стабильный выпуск с appcast; не выбирайте старый выпуск вручную как latest. Приложение сверяет версии через Sparkle и не предлагает downgrade. DMG предназначен для первой установки; обновления используют ZIP. Squirrel `latest-mac.yml` и blockmap не используются (builder может создать неиспользуемый ZIP blockmap, он не публикуется).

В `.github/workflows/release.yml` macOS-проверки и упаковка используют hosted Apple silicon `xcode-27`, подготовка и публикация — Ubuntu. Desktop/workflows-проверки выполняются отдельно от упаковки; публикация ждёт успеха всех проверок. Готовые app/native outputs повторно используются через `npm run release -- --prebuilt`, затем загружаются архивы и appcast и публикуется черновик при ручном запуске. Защищённая environment `release` хранит ключ Sparkle и сертификат подписи и может требовать approval владельца.

## Поведение приложения

Выпуск проверяет обновления при запуске и затем каждые шесть часов. Найденный ZIP загружается и проверяется в фоне; настройки показывают прогресс, затем «Установить и перезапустить». Сеть или неправильная подпись дают ошибку с возможностью повторной проверки и не мешают работе полки. Локальные/CI-сборки не обращаются к feed.

Стартовая полка и основные настройки показывают компактное уведомление новой версии в две строки: состояние и действия. На полке уведомление прокручивается вместе со списком приложений. «Что нового» открывает полные примечания «Русский / English» во вкладке «О приложении». «Обновить и перезапустить» доступно после загрузки; «Пропустить эту версию» скрывает только выбранную версию, включая последующие запуски. «Напомнить завтра» откладывает карточку на 24 часа, включая перезапуски; по истечении срока карточка возвращается и в уже работающем приложении. Более новая версия показывается сразу. Выбор хранится в настройках профиля. Пропущенное или отложенное обновление можно установить в «О приложении → Обновления».

Карточка доступна начиная с 0.3.0. Пользователь более ранней версии сначала устанавливает 0.3.0 или новее через прежний интерфейс «О приложении → Обновления» или DMG; новая карточка появляется для следующих обновлений.

Перед явной установкой окна блокируют ввод и сохраняется история буфера. Ошибка сохранения отменяет перезапуск, сохраняет готовое обновление и восстанавливает окна. Worker настроек остаётся запущенным, пока Sparkle подготавливает обновление; при ошибке staging окна снова доступны. Native-событие `before-quit-for-update` запускает штатный выход Electron с остановкой полки, индикатора и worker настроек. При обычном выходе история также сохраняется. Данные живут в пользовательском профиле вне `.app` и не заменяются updater.

Стандартный Sparkle может установить staged update при обычном выходе. Поэтому `scripts/release/sparkle-bridge.patch` добавляет native API отмены staging и событие готовности installer к pinned bridge. Событие запускает штатный Electron quit только после подготовки installer. `node scripts/release/build-sparkle.mjs` применяет патч идемпотентно и прекращает сборку, если исходник изменился. Обычный выход после сохранения вызывает отмену; явный update restart сохраняет staging. Автоустановка при обычном выходе не разрешена. При обновлении bridge этот патч и smoke необходимо пересмотреть.

## Проверка настоящего обновления

`npm run test:desktop -- updates` собирает два реальных ad-hoc `.app` с отдельным appId, временным Ed25519 ключом и localhost feed. Проверяет отклонение неправильной подписи, автоматическую загрузку, отсутствие установки до подтверждения, отмену staging при обычном выходе, установку/перезапуск новой версии и сохранность пользовательской настройки. Тест использует отдельный временный AES-ключ вместо login Keychain, поэтому не вызывает системные запросы пароля и не проверяет перенос Keychain-разрешений. Тест ничего не публикует, не использует production ключи и удаляет свои bundles/profile. Нужна desktop-сессия macOS; runner автоматически убирает `ELECTRON_RUN_AS_NODE` из окружения дочерних проверок.

`npm run test:desktop -- updates --self-signed` проверяет тот же installer/relaunch с двумя self-signed Electron bundles и одноразовым тестовым сертификатом. До упаковки и после установки сверяет DR приложения и всех Swift helpers. `npm run test:desktop -- updates --migrate-self-signed` проверяет установку self-signed версии поверх прежней ad-hoc версии через Sparkle с неизменным Ed25519 ключом. `tests/integration/mac-signing.test.ts` дополнительно собирает два разных Mach-O, проверяет соответствие новой версии прежним requirements, отказ при неправильном сертификате/identifier/ad-hoc helper и удаление временного keychain при ошибке. Эти тесты не запрашивают Accessibility-разрешение и не доказывают сохранение TCC grants.

Приёмка разрешений перед production выпуском:

1. Установить первую self-signed версию в `/Applications/Polka.app`, заново выдать Accessibility-разрешение и убедиться, что история вставляется в другую программу.
2. Обновить через настоящий Sparkle feed на вторую версию с тем же сертификатом, сохранив ключ Sparkle и appId.
3. Без переключения разрешения в Settings вставить элемент истории в другую программу. Повторить после обычного перезапуска Polka. Проверить доступ к сохранённой истории через `safeStorage`.
4. Зафиксировать macOS version/build и результат. Если переключатель включён, а helper возвращает `trusted: false`, собрать TCC diagnostics и не считать сохранение разрешений подтверждённым.

Отдельная приёмка перед первым production выпуском также включает чистый Mac, первый Gatekeeper launch, права администратора и доставку через GitHub. Старые установки без Sparkle требуют одного ручного обновления.
